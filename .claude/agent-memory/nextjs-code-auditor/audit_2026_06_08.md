Audit date: 2026-06-08

## Critical (1)
- All DB query functions called from dashboard/items pages (getPinnedItems, getRecentItems, getDashboardCollections, getDashboardStats, getSidebarData, getItemsByType) have NO userId filter. Multi-tenant data leak — every authenticated user sees every other user's data.

## High (3)
- upload API returns the R2 fileUrl to the client, which then passes it verbatim to the createItem server action. No server-side verification that the stored fileUrl was issued to the current user's path. A user could supply any R2 URL.
- getItemsByType() has no `take` limit — full table scan as data grows.
- getPinnedItems() has no `take` limit — could return unbounded rows.

## Medium (3)
- updateItemById and deleteItemById each do 2 separate DB round-trips (existence check + operation). Should be folded into one.
- Content-Disposition header in download route uses double-quoted filename with encodeURIComponent — RFC 6266 requires `filename*=UTF-8''...` encoding for non-ASCII names; current approach breaks downloads of files with non-ASCII names.
- formatBytes() and formatDate() duplicated across ItemDrawer.tsx, FileRow.tsx, and ItemCard.tsx.

## Low (1)
- resendVerification rate limiter is defined in rate-limit.ts but never wired up to any route.

## Already Correct
- All API routes that mutate data check auth() and return 401
- ItemDrawer fetch is scoped to the authenticated user via getItemById(userId, id)
- Download route scopes by userId — no IDOR on downloads
- createItemInDb correctly scopes item to the authenticated userId
- updateItemById and deleteItemById both accept userId and enforce ownership
- Rate limiting on register, forgot-password, reset-password, and login
- Fail-open rate limit behavior (allows requests when Upstash is unreachable)
- No hardcoded secrets in source files
- Zod validation on all server actions
- JWT strategy with session.user.id set from token.sub
- Email verification blocks unverified Credentials users
